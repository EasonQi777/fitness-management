# 健身房会员办卡订单管理后台

连锁健身房会员办卡订单的中文管理后台：登录、订单列表、新建订单、续卡、撤单、CSV 导出。数据由项目内的内存模拟服务提供，无需后端。

**技术栈**：React 18 · Vite 8 · React Router 7 · Ant Design 5 · Tailwind CSS 4 · axios · zustand · dayjs · Vitest · Testing Library · Playwright

## 快速开始

需要 Node.js 24.12.0 与 npm。

```bash
npm ci
npm run dev        # http://localhost:5173，任意非空账号密码登录
```

| 命令                                    | 用途                     |
| --------------------------------------- | ------------------------ |
| `npm run build` / `npm run preview`     | 生产构建 / 本地预览      |
| `npm run lint` / `npm run format:check` | 代码检查 / 格式检查      |
| `npm run test`                          | 单元与交互测试（Vitest） |
| `npm run test:e2e`                      | 端到端测试（Playwright） |

订单数据保存在浏览器内存中，刷新页面恢复为 36 笔初始订单，登录状态保留。

## 功能

- **登录与布局**：模拟登录、路由守卫与登录回跳、后台布局（菜单、顶栏、面包屑）、404。
- **订单列表**：状态 Tab、订单号精确 / 姓名模糊搜索、分页、状态 Tag、金额千分位；条件保存在 URL 中。
- **续卡与撤单**：单条与批量续卡（实时计价、满 5 年八折）、批量撤单（二次确认列出订单号）；不符合条件的订单在提交前即提示。
- **新建订单**：表单验证、实时费用、未保存内容离开提示，提交后回到列表首行可见。
- **CSV 导出**：导出筛选结果或勾选记录，先预览可导出与被排除的订单，确认后下载。
- **其余项**：跨页、跨 Tab 保留勾选；列表查询封装为 `useOrders`。

## 工程亮点

- **写操作可靠**：幂等键防止重复提交，订单版本号拒绝基于过期数据的操作，批量操作整批校验、原子写入；写入后自动回到有效页，写入成功但刷新失败时单独提示，不会诱导重复操作。
- **查询无竞态**：条件变化时取消旧请求，只采用最新请求的结果；URL 保存已提交条件，刷新与前进后退可恢复。
- **会话安全**：退出与 401 共用一个清理流程；并发 401 只提示一次，上一位员工的迟到 401 不会影响新登录；登录回跳地址白名单防止开放重定向。
- **导出可控**：服务端最终判断导出资格，下载内容与确认的预览一致；CSV 使用 UTF-8 BOM、完整转义并防止公式注入，不导出手机号与备注。
- **异常可复现**：通过环境变量开启查询失败、写入失败、登录失效与慢查询，默认关闭，用于演示与测试。
- **测试完整**：743 个单元与交互测试（多次打乱顺序运行均通过）、21 个 Playwright 端到端测试（真实下载文件、跨页批量操作、异常场景、三种屏幕宽度、键盘操作）；GitHub Actions 在 PR 上自动检查。
- **响应式与可访问性**：1440 / 768 / 390px 均可完成主要操作；全流程可用键盘完成，表单错误关联到字段，弹窗关闭后焦点回到触发按钮。

├─ store/        zustand 认证状态、退出与 401 清理

## 请求层与状态管理

**请求层**：统一的 axios 实例（`baseURL: /api`）通过自定义 adapter 接入内存模拟服务，接入真实后端只需移除 adapter。请求拦截器注入最新 token；响应拦截器将错误分为普通错误（统一提示）、字段错误与批量错误（交给页面展示）、401（统一退出）和取消（静默）。

**状态管理**：

| 状态                 | 位置                                                |
| -------------------- | --------------------------------------------------- |
| 登录信息             | zustand（localStorage 持久化，仅存 token 与用户名） |
| 已提交的查询条件     | URL                                                 |
| 列表数据、加载、错误 | `useOrders`                                         |
| 跨页勾选             | `useOrderSelection`                                 |
| 弹窗、表单、提交锁   | 页面局部 state                                      |
| 业务规则             | `src/domain/`，页面与模拟服务共用                   |

## 模拟数据与异常场景

模拟服务支持查询与真实写入（新建、续卡、撤单），包含版本校验、幂等处理和操作日志。复制 `.env.example` 为 `.env.local` 并重启 `npm run dev` 可开启：

- `VITE_MOCK_FAIL_QUERY=N` / `VITE_MOCK_FAIL_WRITE=N`：接下来 N 次查询 / 写入失败
- `VITE_MOCK_UNAUTHORIZED=N`：接下来 N 次请求返回 401
- `VITE_MOCK_SLOW_QUERY=袁:3000`：姓名含“袁”的查询延迟 3 秒，用于观察查询竞态
- `VITE_MOCK_DATASET=bulk`：加载批量数据集（已到期、可撤单订单均超过一页）

## Part 5：导出需求

> 列表页帮我们加个导出功能吧，把订单数据导出来给财务对账用，金额格式弄得好看一点。对了，上次权限评审的时候说过，有些状态的订单是不能随便导出的，具体哪些你看着办。

### 澄清问题

1. 导出当前页、全部筛选结果，还是勾选的记录？
2. 哪些状态允许导出？不同角色权限是否不同？
3. 财务对账需要哪些字段？是否需要手机号、备注？
4. 订单金额是首次购卡金额、累计收款，还是最近一次交易金额？
5. 金额用于阅读，还是需要在表格中直接求和？
6. 空金额代表未知、未付款还是零？
7. 创建时间按哪个时区导出？
8. 混入不可导出的订单时，整批拒绝还是排除后导出？

### 实现假设（均待业务确认）

1. 提供“导出筛选结果”（全部分页）与“导出勾选记录”（跨页勾选）两个入口。
2. 仅“已完成”“已到期”可导出；其他状态在预览中列出订单号与原因后排除。
3. 所有登录用户使用同一规则，由模拟服务最终校验（生产环境应由后端权限系统负责）。
4. 字段：订单号、会员姓名、购卡年限、订单金额、状态、创建时间；不导出手机号与备注。
5. 金额为订单当前金额，格式 `12,000.00`；`0` 输出 `0.00`，空金额输出空单元格。千分位金额为文本，表格中不能直接求和。
6. 文件为 UTF-8 BOM、CRLF、中文表头；防止公式注入；时间按上海时区。
7. 先预览再下载，下载内容为确认时的预览快照；无可导出记录时不生成文件。

## 其他需求理解

| 需求原文或问题                                   | 处理                                             |
| ------------------------------------------------ | ------------------------------------------------ |
| “按创建时间**升序**，保证最新订单在最前”（矛盾） | 以“最新在最前”为准，按创建时间降序               |
| “任意账号密码均可登录”                           | 账号、密码需非空                                 |
| 续卡费用是否计入订单金额                         | 订单金额保留原值，续卡费用记入操作日志（待确认） |
| 接口可能返回空金额                               | 列表显示 `—`，与 `0.00` 区分                     |
| 批量操作混入不符合条件的订单                     | 整批拒绝并列出订单号与原因，不做部分成功         |
| 手机号地区、展示时区                             | 中国大陆 11 位手机号；`Asia/Shanghai`（待确认）  |

## 开发中最难的问题

**搜索框的新输入被上一次条件覆盖。** 在“先搜‘袁’（慢查询），马上改搜‘王’”的端到端测试中偶发失败，失败时搜索框里的“王”变回了“袁”。

- **原因**：已提交的条件保存在 URL，页面在 URL 变化时回填输入框。React Router 异步更新地址，用户在地址更新前继续输入，回填会覆盖新输入，第二次查询提交的仍是旧条件。
- **解决**：记录本页提交的内容；由该次提交引起的 URL 变化，若输入框已被继续修改则不回填，浏览器前进后退仍正常回填。
- **验证**：jsdom 中无法复现同一时序，以浏览器端到端测试作为回归依据，修复后连续 15 次运行通过。

类似的时序问题还有：换人登录后上一位员工的旧请求返回 401——只处理携带当前 token 的 401，避免误踢新登录的用户。
