# 健身房会员办卡订单管理后台

连锁健身房会员办卡订单的中文管理后台：登录、订单列表（筛选 / 搜索 / 分页）、新建订单、续卡、撤单、CSV 导出。数据由项目内的内存模拟服务提供，无需启动后端。

需求来源：前端工程师笔试题（健身房会员办卡订单管理模块）。

## 快速开始

需要 Node.js 24.12.0（或满足下方“运行环境”的版本）与 npm。

```bash
npm ci
npm run dev
```

打开 http://localhost:5173 ，任意**非空**账号与密码即可登录（例如账号 `wangfang`）。订单数据只保存在浏览器内存中，**刷新页面会恢复为初始的 36 笔演示订单**，登录状态保留。

## 请求层、认证与状态管理设计

### 请求层

- **axios 实例**（`src/api/http.js`）：`baseURL` 为 `/api`，adapter 为项目内的模拟服务。页面只调用 `src/api/orders.js`、`src/api/auth.js` 中的接口函数，不直接接触模拟数据；接入真实后端时去掉自定义 adapter 即可。
- **请求拦截器**：每次请求时从 zustand 读取最新 token，注入 `Authorization: Bearer <token>`，换人登录后不会沿用旧 token。
- **响应拦截器**：用 `parseApiError` 把失败分为五类——请求取消不提示；普通错误（网络、服务异常）由请求层统一提示，相同文案并发时只显示一条；字段错误、批量业务错误交给页面展示在对应位置；401 走统一退出流程。只有**携带当前 token** 的 401 才会结束会话，因此并发的多个 401 只提示一次，上一位员工的旧请求迟到的 401 也不会把新登录的员工踢出。
- **写操作**：新建、续卡、撤单携带 `Idempotency-Key`。页面为每次提交意图生成一个键，原样重试（如网络超时后再点确认）复用该键，修改输入后换新键；续卡、撤单还携带订单版本号，服务端据此拒绝基于过期数据的操作。
- **模拟服务**（`src/mock/`）：adapter 模拟 300ms 网络延迟、支持取消，并以 JSON 字符串返回，页面拿到的是副本；`server.js` 负责路由与 token 校验；`writes.js` 统一处理幂等、订单引用与版本校验、整批原子写入。

### 认证

- **zustand `authStore`** 是唯一读写 localStorage 认证信息的位置（键 `fitness-management:auth`），只保存 token 与用户名，不保存密码；启动时恢复，数据损坏时清除并按未登录处理。
- **路由守卫**：未登录访问受保护页面时跳到 `/login?redirect=...`，登录后回到原页面（回跳地址只允许 `/orders`、`/orders/new` 及其查询参数，防止开放重定向）；已登录访问登录页时直接进入列表。
- **退出与 401 共用一个清理流程**（`src/store/session.js`）：清除认证后受保护页面立即卸载，页面内的勾选、表单、弹窗随之释放，进行中的查询被取消；主动退出时若新建订单表单有未提交内容，先确认。
- 模拟 token 为 `mock.` + Base64(JSON)，无签名，仅做格式校验；真实服务端应使用签名 token。

### 状态管理

| 状态                                | 位置                   | 说明                                                              |
| ----------------------------------- | ---------------------- | ----------------------------------------------------------------- |
| 登录信息                            | zustand `authStore`    | 全局唯一需要跨页面共享的状态                                      |
| 已提交的查询条件（Tab、搜索、分页） | URL（`useOrderQuery`） | 刷新、前进后退、分享链接都能恢复；输入框中的内容只是草稿          |
| 列表数据、加载、错误                | `useOrders`            | 条件变化时取消旧请求，只采用最新请求的结果，避免慢响应覆盖新结果  |
| 跨页勾选                            | `useOrderSelection`    | 以订单 ID 保存快照，跨页、跨 Tab 保留；当前页出现时用最新数据更新 |
| 弹窗、表单、提交锁                  | 页面局部 state         | 随页面卸载释放，退出登录后不会残留                                |
| 未保存表单标记                      | zustand `unsavedStore` | 供顶栏“退出登录”判断是否需要确认                                  |
| 业务规则                            | `src/domain/`          | 状态资格、价格、表单验证由页面与模拟服务共用，前后端结论一致      |

## 模拟数据与异常场景

- 订单数据只保存在浏览器内存中。**刷新页面会把订单恢复为初始数据**，新建、续卡、撤单的结果随之丢失；登录信息保存在 localStorage，刷新后仍保留。
- 模拟服务仅用于演示前端设计与接口边界，不代表真实的服务端权限控制、持久化或财务账本。
- 测试代码可调用 `resetMockDb()` 重置为初始数据或换用批量测试数据集；页面不提供重置入口。

### 异常场景配置

用于演示和验证失败提示、重试、登录失效与查询竞态。**默认全部关闭**，普通启动不会随机失败；开启后浏览器控制台会打印 `[mock] 已启用异常场景`。

1. 复制 `.env.example` 为 `.env.local`，取消需要的那一行注释；
2. 重启 `npm run dev`（Vite 只在启动时读取环境变量）。

| 环境变量                           | 效果                                                                                                            |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `VITE_MOCK_FAIL_QUERY=N`           | 页面加载后接下来 N 次订单列表查询返回 500，之后恢复，可点“重试”验证                                             |
| `VITE_MOCK_FAIL_WRITE=N`           | 接下来 N 次新建、续卡、撤单返回 500；在修改数据之前失败，订单、操作日志都不变                                   |
| `VITE_MOCK_UNAUTHORIZED=N`         | 接下来 N 次受保护请求返回 401，页面提示一次“登录已失效”并回到登录页                                             |
| `VITE_MOCK_SLOW_QUERY=关键词:毫秒` | 会员姓名包含该关键词的列表查询额外等待，如 `袁:3000`；先搜“袁”再马上搜其他条件，页面只显示最后一次的结果        |
| `VITE_MOCK_DATASET=bulk`           | 加载批量测试数据集（33 笔，已到期 15 笔、可撤单 13 笔，均超过一页），用于演示跨页批量操作；默认为 36 笔演示数据 |

计数保存在内存中，刷新页面后按配置重新计数。Vitest 不读取这些环境变量，测试通过 `setFaults()` 按需开启，每个测试结束后自动恢复默认（`src/test/setup.js`）。Playwright 另起一个开启异常场景的开发服务（5175 端口，见 `playwright.config.js` 的 `faults` 项目），主流程测试使用的 5174 服务不受影响。

## 接口契约

所有请求以 `/api` 为前缀，由 axios 自定义 adapter 交给内存模拟服务处理。除登录外均需 `Authorization: Bearer <token>`。写操作需 `Idempotency-Key` 请求头。

| 接口                          | 请求                                                                                                                                                                                                                                                                              | 成功响应                                                                                                                                                                                                                                       |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/login`            | `{ username, password }`                                                                                                                                                                                                                                                          | `{ token, username }`                                                                                                                                                                                                                          |
| `GET /orders`                 | 查询参数 `tab`（`all` / `in_progress` / `expired` / `completed` / `cancelled`，默认 `all`）、`orderNo`（去首尾空格后精确匹配）、`memberName`（去首尾空格后包含匹配，不区分大小写）、`page`（正整数，默认 1）、`pageSize`（10 / 20 / 50，默认 10）；条件为 AND，参数不合法返回 400 | `{ items, total, page, pageSize }`；按创建时间降序、同时间按 ID 升序；`total` 为分页前的匹配数；页码超出范围时 `items` 为空                                                                                                                    |
| `POST /orders`                | `{ memberName, phone, cardYears, remark }`，需 `Idempotency-Key`；校验规则与页面表单相同，字段错误以 `fieldErrors` 返回                                                                                                                                                           | 新建的订单：服务端生成 ID、订单号（`FM` + 上海日期 + 当日序号）与创建时间，金额 = 年限 × 1200，状态待审核，版本 1；忽略页面传入的金额、状态与编号                                                                                              |
| `POST /orders/renew`          | `{ orders: [{ id, version }], years }`，需 `Idempotency-Key`；`years` 为 1–10 整数，错误以 `fieldErrors.years` 返回；仅已到期订单可续                                                                                                                                             | `{ orders, unitPrice, totalPrice }`：累计年限增加、状态改待审核、版本加 1，金额与创建时间不变；`unitPrice` 为单笔续卡费用（≥ 5 年八折），`totalPrice` = 单笔 × 订单数                                                                          |
| `POST /orders/cancel`         | `{ orders: [{ id, version }] }`，需 `Idempotency-Key`；仅待制卡、待寄卡订单可撤                                                                                                                                                                                                   | `{ orders }`：状态改已取消、版本加 1，金额、年限与创建时间不变                                                                                                                                                                                 |
| `POST /orders/export-preview` | `{ scope: 'filtered', filters: { tab, orderNo, memberName } }`（与列表相同的筛选规则，不分页）或 `{ scope: 'selected', ids }`（勾选的订单 ID，可跨页、跨状态，不可为空或重复）；只读，不需要幂等键                                                                                | `{ items, excluded: [{ id, orderNo, reason }] }`：`items` 为已完成、已到期订单，按创建时间降序，只含 `id、orderNo、memberName、cardYears、amount、status、createdAt`；其他状态及不存在的 ID 列入 `excluded`（不存在时 `orderNo` 为 `null`）    |
| `GET /operation-logs`         | —                                                                                                                                                                                                                                                                                 | `{ items }`，按发生先后排列，每笔订单一条：`{ id, action（create / renew / cancel）, operator, operatedAt, orderId, orderNo, fromStatus, toStatus, renewYears?, renewFee? }`；只记录成功的写入，幂等重放不重复记录；仅供验证与调试，不建设页面 |

错误响应体统一为 `{ code, message, fieldErrors?, invalidOrders? }`，`invalidOrders` 每项为 `{ id, orderNo, reason }`（订单不存在时 `orderNo` 为 `null`）。定义见 `src/api/errors.js`。

| HTTP | `code`                 | 场景                                 | 页面处理（`parseApiError` 的 `kind`）                    |
| ---- | ---------------------- | ------------------------------------ | -------------------------------------------------------- |
| 400  | `VALIDATION_ERROR`     | 参数错误；表单错误附带 `fieldErrors` | 有 `fieldErrors` → `field`，显示在字段下；否则 `general` |
| 400  | `INVALID_ORDERS`       | 批量操作含不合格或不存在的订单       | `batch`，列出订单号与原因                                |
| 401  | `UNAUTHORIZED`         | 未登录或 token 无效                  | `unauthorized`，走统一退出流程                           |
| 404  | `NOT_FOUND`            | 接口不存在                           | `general`                                                |
| 409  | `VERSION_CONFLICT`     | 订单版本已变化，附带 `invalidOrders` | `batch`                                                  |
| 409  | `IDEMPOTENCY_CONFLICT` | 同一幂等键对应不同参数               | `general`                                                |
| 500  | `INTERNAL_ERROR`       | 模拟服务错误                         | `general`                                                |

请求被取消时为 `cancelled`，不提示；无响应的网络错误为 `general`。只有 `general` 由请求层统一提示（相同文案并发时只显示一条），其余由页面展示，避免重复提示。页面需要自行展示 `general` 错误时（如登录页、列表失败重试区域），请求配置传 `{ skipErrorToast: true }`。请求拦截器在每次请求时读取最新 token 注入 `Authorization`。

### 写操作规则

新建、续卡、撤单的处理顺序为：认证 → 幂等命中 → 参数与订单校验 → 一次性写入（实现见 `src/mock/writes.js`）。

- **幂等**：请求头 `Idempotency-Key` 必填。同一员工、同一接口、同一幂等键：请求体相同则直接返回首次成功的结果（不再执行，成功后的重试也不会误报版本冲突）；请求体不同返回 409 `IDEMPOTENCY_CONFLICT`。只保存成功结果，校验失败后可用同一个键修正重提。
- **订单引用**：续卡、撤单传 `orders: [{ id, version }]`，依次校验：空集合 / 格式错误 / 重复 ID（400 `VALIDATION_ERROR`）→ 订单不存在（`INVALID_ORDERS`）→ 版本已变化（409 `VERSION_CONFLICT`）→ 业务资格（`INVALID_ORDERS`）。每一步列出全部不合格订单及原因。
- **原子性**：全部校验通过后一次性写入，任一订单不合格则整批不修改。
- **操作日志**：与订单写入同时生效，失败的请求和幂等重放都不产生日志。
- **写入后**：页面重新查询当前条件；若当前页已超出总页数（如末页订单全部移出筛选），自动回到最后有效页（替换历史记录）。写入成功但列表刷新失败时，提示“操作已成功，列表刷新失败”，“重新加载列表”只重新查询，不会再次提交写入。

### 导出文件说明

| 列       | 内容                                            | 示例                  |
| -------- | ----------------------------------------------- | --------------------- |
| 订单号   | 原样输出                                        | `FM20211102001`       |
| 会员姓名 | 原样输出；以公式字符开头时前加 `'`              | `阿依古丽·买买提`     |
| 购卡年限 | 累计年限，整数                                  | `2`                   |
| 订单金额 | 千分位两位小数；`0` 为 `0.00`；空金额为空单元格 | `2,400.00`            |
| 状态     | 中文状态名，只会是“已完成”或“已到期”            | `已到期`              |
| 创建时间 | 上海时间，精确到秒                              | `2021-11-02 09:05:41` |

关于千分位金额：每个单元格都以文本形式写入（带双引号），`12,000.00` 在 Excel、WPS 中通常按文本显示，**不能直接用 SUM 求和**，需要先“分列”或替换掉逗号转为数字。如果财务的主要用途是求和对账，更合适的做法是输出不带千分位的数字 `12000.00`，由表格软件设置显示格式——这需要业务确认后调整 `src/utils/ordersCsv.js` 中的金额列。页面列表中的空金额显示为 `—`，导出时为空单元格，避免对账时被当作字符或零。

## 开发中最难的问题

### 搜索框中的新输入被上一次查询条件覆盖

**现象**：为验证“先慢后快”的查询竞态，在异常场景服务上写了端到端测试：先搜“袁”（被设为慢查询），马上改搜“王”。测试在几次运行中偶发失败，失败时页面显示的是“袁”的结果，**搜索框里的“王”也变回了“袁”**。

**排查**：

1. 先怀疑 `useOrders` 的竞态处理失效（慢响应覆盖了快响应）。但它的单元测试与页面测试都通过，而且失败截图中地址栏也是 `memberName=袁`——说明最终提交的就是“袁”，问题出在提交之前。
2. 输入框是“草稿”，已提交的条件在 URL 中；页面用一个 effect 在 URL 变化时把条件回填到输入框，用于浏览器前进后退时恢复。React Router 更新地址是异步的：点击查询“袁”后、地址真正变为“袁”之前，用户已经输入了“王”；地址更新完成时 effect 把输入框改回“袁”，第二次点击查询提交的也就是“袁”。
3. 尝试在 jsdom 中用同步事件复现，但 antd 表单的校验是异步的，两次提交读到的都是最新值，无法复现同一时序，所以以浏览器中的端到端测试作为回归依据。

**解决**：提交查询时记下提交的内容；随后由这次提交引起的 URL 变化，如果输入框已经和提交时不同（用户继续输入了），就不再回填，保留新草稿；浏览器前进后退等其他来源的变化照常回填。条件未变化（地址不变）时清除记录，避免影响之后的后退。修复后该端到端测试串行重复运行 15 次全部通过。

**体会**：这个问题只在“比人手更快的操作”或较慢的设备上出现，是异常场景配置（慢查询）与端到端测试一起暴露出来的；单元测试中的同步环境掩盖了它。

### 其他值得记录的问题

- **换人登录后，上一位员工的旧请求返回 401**：如果按“收到 401 就退出”处理，会把刚登录的店长踢出。解决方法是只处理携带当前 token 的 401。编写测试时还发现，axios 在异步的请求拦截器中注入 token：如果发出请求后同一时刻就换人登录，这个“旧请求”实际带的是新 token——测试需要等请求真正发出后再换人。
- **弹窗关闭后键盘焦点丢失**：续卡、撤单、导出预览弹窗按需挂载、关闭即卸载，antd 无法把焦点还给触发按钮。新增 `useRestoreFocus`：首次渲染时记下触发按钮，卸载后焦点落回页面开头时才还原，避免与 React StrictMode 开发环境的模拟卸载冲突。
- **测试的真实性**：早期部分测试直接改写模拟数据库、编造服务端不会返回的响应。后来统一改为真实流程：用另一个员工账号真实调用接口制造“他人先修改”，用异常场景开关让模拟服务返回真实的 500、401 与慢响应。
